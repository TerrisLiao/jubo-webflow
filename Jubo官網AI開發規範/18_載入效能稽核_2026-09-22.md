# 18｜載入效能稽核報告（2026-09-22）

> 起因：Terris 用手機無痕模式開官網「完全讀不出來」，PageSpeed Insights 行動版分數 89 但多項紅字。
> 稽核方式：**實際抓線上頁面 + Chromium 無痕情境實測**（非讀 repo 快照）。
> 實測環境：Pixel 7 emulation、全新 context（無 cookie／無快取，等同無痕）、CPU 4× 降速。
> 網速條件分兩檔：**4G**（1.6 Mbps／150ms RTT）與 **Slow 3G**（400 Kbps／400ms RTT）。
> 站台：`www.jubo-health.com`（site id `69ec2b02daa2e79f1da8772a`），發布時間 2026-09-22 09:38 UTC。

## 0. 一句話結論

**不是「讀不出來」，是「載太久」。** 首頁在 4G 冷快取要 14.8 秒才跑完 load，Slow 3G 要 **59 秒**；
`/news` 更誇張，4G 就要 **48.5 秒、9.4 MB**。其中 **94% 是圖片**，而圖片爆量的單一根因是
**CMS 封面圖用 CSS `background-image` 輸出，Webflow 的 responsive 圖片機制完全失效**。

## 2. 問題清單（按影響程度排序）

### 🔴 P0-1　CMS 封面圖用 `background-image`，responsive 圖片機制整組失效

**這是最大單一根因，佔 `/news` 全頁 94% 的流量。**

| class | 用在哪 | 張數 | 顯示尺寸（手機） | 實際下載 |
|---|---|---|---|---|
| `.single-news_cover-img` | `/news` 列表卡片 | 54 | 388 × 218 px | 每張 275–426 KiB，**合計 8.9 MB** |
| `.cases-img` | 首頁客戶案例／見證 | 15 | 336 × 496 px | 最大單張 **842 KiB**（`cases-3.png`） |

實測：
- `img 有 srcset 的比例：/news 12/15、首頁 25/40`
- `background-image 張數（永遠無 srcset）：/news 54、首頁 15`

**為什麼嚴重**：Webflow 只有在使用 **Image 元素（`<img>`）** 時才會自動產生
`-p-500 / -p-800 / -p-1080 / -p-1600` 變體並輸出 `srcset` + `sizes` + `loading="lazy"`。
一旦改用 div 的 background-image，這整套機制**完全不會啟動** —
不管螢幕多小，一律下載原始檔，而且不會 lazy load。

首頁單張 `cases-3.png`：**842 KiB PNG，塞進 336×496 的卡片**，
一張就佔首頁全部圖片流量（1,831 KiB）的 **46%**。

**建議修法**（由 Webflow Designer 操作，需授權）：
1. 把 `.single-news_cover-img` 與 `.cases-img` 從「div + CMS background image」
   改成「**Image 元素綁 CMS 圖片欄位**」，外層 wrapper 保留現有 class 控尺寸、圓角、`object-fit: cover`。
2. 改完 Webflow 會自動補 `srcset`／`sizes`／`loading="lazy"`。
3. 預估 `/news` 從 9.4 MB → **約 0.8–1.2 MB**（減 ~88%）；首頁從 2.37 MB → **約 1.1 MB**。

> ⚠️ `.cases-img`、`.single-news_cover-img` 都未列在 `custom-code/slater-selectors.md`，
> 但改結構前仍須先全站搜尋 class 使用情況與 Slater 檔案，確認沒有其他依賴。

### 🟠 P1-1　Slater 的 CSS／JS 被設成 `cache-control: no-store`，每次瀏覽都重下載

```
https://slater.app/20018/60294.css   →  cache-control: no-store   （render-blocking，在 <head>）
https://slater.app/20018/60292.js    →  cache-control: no-store   （92 KB，全站互動）
```

**`no-store` 代表瀏覽器連「暫存一份」都不准**，所以：
- 使用者每開一頁、每次上一頁／下一頁，都要重新連 `slater.app` 抓一次
- 實測 `slater.app` TTFB **376–400 ms**（同一時間 jsDelivr 只要 120–150 ms）—— 它不是 CDN
- head 裡沒有對 `slater.app` 下 `preconnect`，等於每頁都要重新做 DNS + TLS 握手

這就是 PSI「**Use efficient cache lifetimes — 423 KiB**」的主要來源。

**實測 Slater 的影響範圍**（把 `slater.app` 全部擋掉再跑一次）：

| | 正常 | Slater 被擋 |
|---|---|---|
| FCP | 1,872 ms | 1,464 ms（**快 400ms**） |
| 頁面是否還能看 | 是 | 是（版面正常、CTA 顏色正常、導覽正常） |
| `window.lenis` | 有 | **無**（平滑捲動失效） |
| 頁面文字量 | 4,615 字 | 3,291 字（部分由 JS 產生的內容消失） |

→ Slater 掛掉不會白畫面，但**平滑捲動、輪播、mega menu 等互動會整組失效**，
且它那支 render-blocking 的 CSS 讓每一頁的首次繪製都多等 ~400ms。

> **注意：這不是「有人把 Slater 改壞了」。**
> 兩個檔案的回應標頭完全一致（`no-store`、無 `last-modified`），看起來是
> **Slater 平台自己的託管行為**，不是 Jubo 這邊設定出來的，也沒有 UI 可以改。
> 這個狀態從掛上去那天就是如此，不是近期的變動。
> （限制：無法讀取 Slater 後台，以上是從 HTTP 標頭推論。）

**建議**（由於快取政策改不了，方向是「搬離 Slater」而不是「調 Slater 設定」）：
1. `60294.css` 壓縮後只有 **3.6 KiB** —— 直接把內容貼進 Webflow Site Settings 的 head
   `<style>` 內嵌，整趟往返直接消失，順便解決 P1-2 的字體問題。
2. `60292.js`（92 KB）搬到 Webflow Custom Code，或放上有正常快取的 CDN。
   搬動時務必比對 `custom-code/slater-selectors.md`，確認 class 依賴不變。
3. 若短期內不搬：先在 `<head>` 最前面加
   `<link rel="preconnect" href="https://slater.app" crossorigin>`（治標，省掉每頁的 DNS + TLS 握手）。

### 🟠 P1-2　Slater CSS 的 `body *` 全域 `!important`，把品牌字體改壞了

`slater.app/20018/60294.css` 第 51–55 行：

```css
/* Apply globally */
body,
body * {
  font-family: 'JuboFont', 'Noto Sans TC', sans-serif !important;
}
```

而 `JuboFont` 的定義（同檔 6–48 行）**只有 `local()` 來源，沒有任何 `url()`**：

```css
@font-face {
  font-family: 'JuboFont';
  font-weight: 400;
  src: local('Poppins'), local('Poppins-Regular');   /* ← 只吃使用者電腦裡裝好的字體 */
  unicode-range: U+0000-00FF, ...;                   /* 拉丁字 */
}
```

`'Noto Sans TC'` 同樣**只是一個字體名稱，站上沒有任何地方去下載它**。

**實測結果**（Chrome DevTools Protocol `CSS.getPlatformFontsForNode`）：

```
document.fonts 狀態：   JuboFont 300 → error
                        JuboFont 400 → error
                        JuboFont 500 → error
h1   實際用的字體 →  [{"familyName":"WenQuanYi Zen Hei","isCustomFont":false}]
.text-size-medium →  [{"familyName":"Liberation Sans","isCustomFont":false},
                      {"familyName":"WenQuanYi Zen Hei","isCustomFont":false}]
```

`isCustomFont: false` = **完全沒有用到任何網頁字體，全部是系統預設字體**。

更矛盾的是：把 Slater 擋掉之後，`body` 的 font-family 變回 Webflow 自己設定的
`Poppins, sans-serif` —— 也就是 **Slater 這條規則正在主動蓋掉站上原本正常運作的 Poppins**。

同時 `<head>` 還在用 WebFont Loader 載 Poppins 五個字重：

```html
<script src="https://ajax.googleapis.com/ajax/libs/webfont/1.6.26/webfont.js"></script>
<script>WebFont.load({ google: { families: ["Poppins:300,400,500,600,700"] }});</script>
```

實測這支同步 script 會**卡住 head 解析 ~300ms**，而且因為它是 JS 驅動，
Google Fonts 的 CSS 要到 **1,692 ms** 才發出請求（若改用 `<link>` 可以在 500ms 就開始）。

**結論**：目前站上「英文用 Poppins、中文用 Noto Sans TC」這個設計意圖
**在絕大多數使用者的裝置上是沒有生效的**（只有本機剛好裝了 Poppins 的設計師電腦看得到），
而且不同裝置會長得不一樣。

**建議**（三選一，需 Terris 決定）：
- **A（推薦）**：拿掉 Slater 那段 `body *` `!important`，字體回歸 Webflow Designer 設定；
  中文字體若要指定 Noto Sans TC，用 Google Fonts 正式引入（含 `font-display: swap` 與子集化）。
- **B**：保留 JuboFont 分流設計，但補上真正的 `url()` 來源（自架 woff2）。
- **C**：維持現狀，但要接受「字體隨裝置而異」並在設計規範裡寫清楚。

> 另外：`body *` 這種萬用選擇器套在 **2,518 個 DOM 節點**上，本身也是不必要的樣式計算成本。

### 🟠 P1-3　render-blocking 資源過多，首次繪製被壓在 1.7–1.8 秒

`<head>` 裡目前有 **3 個 CSS + 3 個同步 JS**，全部都會擋住繪製：

| 資源 | 4G 實測完成時間 |
|---|---|
| `ajax.googleapis.com/.../webfont.js`（同步） | 813 ms |
| `jsdelivr/@finsweet/attributes@2/attributes.js` | 977 ms |
| `jsdelivr/swiper@12/swiper-bundle.min.css` | 1,042 ms |
| `jsdelivr/@flowbase-co/boosters-countup` | 1,078 ms |
| `jsdelivr/lenis@1.1.13/lenis.min.js`（同步） | 1,106 ms |
| `slater.app/20018/60294.css` | 1,121 ms |
| `jsdelivr/@finsweet/cookie-consent@1/fs-cc.js` | 1,507 ms |
| **`cdn.prod.website-files.com/.../jubo-health.webflow.shared.css`** | **1,650 ms** |
| → first-paint | **1,736 ms** |

first-paint 幾乎等於最後一支 CSS 下載完的時間 —— 這就是 PSI「**Render-blocking requests
— 1,200 ms**」的來源。

`</body>` 前又有 **6 支同步 script**（`gsap` / `ScrollTrigger` / `Draggable` /
`InertiaPlugin` / `swiper-bundle` / `slater 60292.js`），全部沒有 `defer`，
這是 DOMContentLoaded 拖到 **7,223 ms** 的主因。

**建議**：
1. `lenis.min.js`、`countup.min.js` 加 `defer`（它們不需要在解析階段執行）。
2. 底部 6 支 script 全部加 `defer`，並確認 Slater JS 的執行時機仍正確。
3. `swiper-bundle.min.css`（3 KiB）改成 `media="print" onload="this.media='all'"` 非阻塞載入，
   或直接內嵌。
4. **`InertiaPlugin` 與 `Draggable`（合計 17 KiB gz）先確認首頁真的有用到**，
   沒用到的頁面不該載。
5. `webfont.js` 整支移除（見 P1-2）。

### 🟢 P3-1　首頁 Organization JSON-LD 有兩處明顯錯誤

`<head>` 的結構化資料：

```json
"aggregateRating": { "@type":"AggregateRating", "ratingValue":"5", "reviewCount":"2700", "bestRating":"5" },
"numberOfEmployees": { "@type":"QuantitativeValue", "value":"330000" },
"url": "/",
"member": [ { "@type":"Person", "jobTitle":"AI資料科學家" }, ... ]
```

問題：
1. **`numberOfEmployees: 330000`** —— 33 萬名員工。這顯然是誤植（可能想寫「服務 33 萬長者」）。
2. **`aggregateRating` 掛在 Organization 上**：Google 不支援 Organization 的 aggregateRating，
   而且「自己幫自己打 5 星、2700 則評論」屬於自我聲明評分，
   依 Google 結構化資料政策有**被人工處罰的風險**。建議直接移除。
3. `"url": "/"` 應該是絕對網址 `https://www.jubo-health.com/`。
4. `member` 裡的 Person 全部只有 `jobTitle`、沒有 `name`，對 Google 沒有意義，建議移除。
