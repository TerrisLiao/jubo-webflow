# 17_效能稽核：首頁載入速度診斷

- 建立日期：2026-09-03
- 對象：`https://www.jubo-health.com/`（首頁）
- 起因：回報官網載入明顯偏慢，且無痕視窗同樣慢（排除本地快取／擴充套件因素）
- 更新：2026-09-03 第二輪複驗，修正兩處過度推論、補上歷史比對與 Swiper 全站掃描結果

## 驗證限制（先讀）

本次診斷以 HTTP 層實測完成，**不是**真實瀏覽器 Lighthouse 跑分：

- 量測機房位於 **AWS us-east-1（維吉尼亞）**，不是台灣。以下所有秒數皆為**最佳情況**；台灣使用者對非 CDN 主機的延遲約為此處的 2–3 倍。
- 本環境的 Chromium 無法穿過 egress proxy（`ERR_CONNECTION_RESET`），因此**沒有實測的 FCP / LCP / TBT / CLS 數字**。
- 相關結論凡屬推估者，下文均標記為「推估」。
- 建議由台灣端補跑 PageSpeed Insights / WebPageTest（Taipei node）取得真實 Core Web Vitals，再據以複驗。

### 第一版的兩處更正

第一版報告有兩點講過頭，這裡更正：

1. **slater.app 的延遲數字被高估。** 首次量到的 `tls: 0.40s / ttfb: 0.45s` 是 proxy 冷啟動的假象。連續 5 次穩態量測後，實際是 slater `ttfb ≈ 0.18s`、jsdelivr `≈ 0.13s`、Webflow CDN `≈ 0.14s`。**從美東看，slater 只慢約 50ms，不是「特別慢」。** 真正的差距在台灣端才會放大（見下）。
2. **Webflow 已對 slater CSS 發送 Early Hints preload。** 實測 `HTTP/2 103` 回應中確實含有 `<https://slater.app/20018/60294.css>; as=style; rel=preload`。也就是說這支檔案的連線與下載**在 HTML 主體到達前就已經開始**，第一版說的「瀏覽器要等 HTML 解析到才發出請求」並不成立。因此「補 preconnect」這條建議作廢。

## 這個問題之前就存在嗎？

**結論：是。這不是最近才出現的迴歸，而是 Webflow 版官網上線起就帶著的結構。**

證據與其限制：

| 查證項目 | 結果 |
|---|---|
| Wayback Machine 存檔 | **沒有任何 Webflow 版的存檔。** 最後一筆 `www.jubo-health.com` 存檔是 2026-06-06，內容仍是舊站 |
| 舊站平台 | `<meta name="generator" content="WordPress 7.0">` + WooCommerce 10.8.1；2025-10 那筆則是 WordPress 6.8.3 + Elementor 3.21.4 |
| 舊站是否有 slater | **無。** 2025-10 / 2026-01 / 2026-05 / 2026-06 四筆存檔中，`slater.app`、`gsap`、`lenis`、`webfont.js` 出現次數皆為 0 |
| Webflow 站建立時間 | Site ID `69ec2b02` 解為 **2026-04-25**；素材 ID 最新為 `6a7549a3` = 2026-08-07 |
| repo 首次記錄 Slater | 2026-08-18（`custom-code/slater-selectors.md`），2026-08-19 commit `9d9f055` |
| `no-store` 是否為近期變動 | 兩支檔案（`60292.js`、`60294.css`）目前皆回 `no-store` + `pragma: no-cache`，`x-runtime` 僅 5–7ms。這是 Slater 平台的一貫行為，不是站方設定 |

因此可以確定：**Slater 的 `no-store` 從 Webflow 版上線第一天就存在。** 若感覺「最近特別慢」，成因比較可能是內容量增長，而不是設定被改壞。

### 舊站 vs 新站的量體比較

| 項目 | 舊站（WordPress，2026-06-06 存檔） | 新站（Webflow，2026-09-03） |

要講公道話：**舊 WordPress 站的 script 與 stylesheet 數量其實更誇張**（43 支 script、39 個 CSS），它也不快，只是慢法不同——當年多數資源同源、可快取。新站把檔案數大幅收斂了，但換來三個新問題：HTML 膨脹成 3 倍、單頁 JS 約 500 KB、以及一個不可快取的第三方關鍵路徑資源。

**限制：** 因為 Wayback 沒有 Webflow 版存檔，我無法量測「新站剛上線時」與「現在」的差異。如果你的體感是最近幾週才變慢，最可能的變因是 8 月新增的內容與素材（例如 2026-08-07 上傳的 353 KB webp），這點需要 Webflow 的發布紀錄才能確認。

| `slater.app/20018/60294.css` | **0** |

**全站沒有任何一處在使用 Swiper。這 170 KB 是純粹的死重。**

## 2. `<head>` 有 3 支 render-blocking script

| 腳本 | 屬性 | 大小 |
|---|---|---|
| `ajax.googleapis.com/.../webfont.js` | **無 defer/async** | 13.2 KB |
| `cdn.jsdelivr.net/npm/lenis@1.1.13/...` | **無 defer/async** | 13.5 KB |
| `.../@flowbase-co/boosters-countup@1.0.0/...` | **無 defer/async** | 2.2 KB |

這三支會直接卡住 HTML parser。其中 `webfont.js` 問題最大：它只是為了載 Poppins 5 個字重，卻造成三段**序列**往返：

```
webfont.js (ajax.googleapis.com)
  → fonts.googleapis.com/css   （JS 執行後才發出）
    → fonts.gstatic.com/*.woff2
```

文字要到第三段回來才會用正確字體渲染。

### 建議
- 移除 `webfont.js`，改用 Webflow 內建的 Google Fonts 設定，或直接在 `<head>` 放 `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Poppins:wght@300..700&display=swap">`。`display=swap` 可避免文字被隱藏。
- `lenis` 與 `countup` 加上 `defer`。兩者都不影響首屏內容。
- 補充：CSS 中的 `Noto Sans TC` 沒有對應 `@font-face`，實際走系統字（PingFang TC / 微軟正黑體）。這點是好的，維持現狀即可，不要改成從 Google Fonts 載中文字體（中文字體檔非常大）。

## 7. 裸網域 301 跳轉不被快取

```
GET https://jubo-health.com/
→ 301 https://www.jubo-health.com/
   cf-cache-status: BYPASS
   cache-control: private
```

使用者若輸入不帶 www 的網址（或舊連結、名片、QR code），會多付一次完整的 DNS + TCP + TLS + 回源往返（美東穩態實測 TTFB 約 0.20s，台灣端推估 0.5s+），且**每次都付**，因為 Cloudflare 對此跳轉是 BYPASS。

### 建議
在 Cloudflare 設定 Redirect Rule（或 Page Rule）處理 apex → www，讓跳轉在邊緣完成並可快取。這需要 Cloudflare 後台權限。

## 8. slater.app：問題屬實，但不可搬動

> **前提更正：** 依 `custom-code/slater-selectors.md`（2026-08-18），Slater 屬於「整個網站的背景設施，不在一般改版的討論與修改範圍內」。第一版報告把「搬進 Webflow」列為第一優先建議，**與此規範牴觸，已撤回。**

首頁載入兩個 slater 資源，皆掛在 Webflow Site Settings → Custom Code：

| 資源 | 位置 | 阻塞 | 大小 |
|---|---|---|---|
| `slater.app/20018/60294.css` | head | render-blocking CSS | 17.9 KB（gzip 3.6 KB） |
| `slater.app/20018/60292.js` | footer | blocking script | 92.9 KB（gzip 19.3 KB） |

### 確認屬實的部分

```
cache-control: no-store
pragma: no-cache
x-runtime: 0.005265
```

`no-store` 代表瀏覽器完全不得快取，每次瀏覽、每次換頁都要重抓。這解釋了「無痕視窗一樣慢」——一般視窗本來也沒有快取可用。

`slater.app` 解析到單一 A record `44.202.1.154`（AWS us-east-1），前端 `via: 1.1 Caddy`，**非 anycast、無亞洲節點**。

### 被高估的部分

- 美東穩態量測：slater `ttfb ≈ 0.18s` vs jsdelivr `≈ 0.13s` vs Webflow CDN `≈ 0.14s`。差距僅約 50ms。
- Webflow 的 `HTTP/2 103` Early Hints **已經對這支 CSS 發 preload**，連線與下載在 HTML 主體到達前就啟動了。

所以在美東，slater 的成本很小。**真正的差距在台灣端**：jsdelivr 與 Webflow CDN 在台灣有節點（RTT 約 10–30ms），slater 必須連到維吉尼亞（RTT 推估 200–250ms）。加上 TCP + TLS + request，單趟推估 0.6–0.8s，且每次載入都要付。

> **這是推估，不是實測。** 需要台灣端 WebPageTest 才能確認。

### 在不搬動 Slater 的前提下能做什麼

老實說：**不多。**

- Early Hints preload 已經在做了，補 `preconnect` 沒有額外效益。
- 把 CSS 改成非阻塞載入（`media="print"` + `onload`）技術上可行，但這支 CSS 含 `@font-face JuboFont` 與 hover／互動樣式，改非阻塞會造成 FOUC 與版面跳動（CLS）。**不建議。**
- `60292.js` 在 footer，加 `defer` 是安全的（見第 3 節），但它依賴 GSAP，必須連同 GSAP 一起 defer 以保留執行順序。

**結論：把 slater 的成本視為固定開銷接受下來，火力集中在其餘 7 項。** 光是第 1 項的 Swiper 就能省下比 slater 兩支檔案加總（110 KB）還多的量。

若未來要處理，唯一的根本解是換到可快取的託管端點；那屬於基礎設施決策，需要另案評估 Slater 方案能力與同步流程成本，不在本次範圍。
